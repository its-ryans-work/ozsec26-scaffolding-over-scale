## Executive Summary

# Penetration Test Report: http://127.0.0.1:5000

## Executive Summary
The assessment identified a critical chain of vulnerabilities stemming from a hardcoded AES-256 symmetric key embedded within the client-side assembly. This key was successfully used to decrypt user tokens containing plaintext passwords, enabling full authentication as an Employee account. Additionally, verbose error handling exposes detailed .NET stack traces with internal file paths. Immediate remediation of the cryptographic implementation, key management, and error handling is required to prevent credential compromise.

---

## Findings

### 1. Hardcoded Cryptographic Key in Client Assembly
- **ID:** secret_aes_key
- **Severity:** Critical
- **Proof Status:** DEMONSTRATED
- **Evidence:**
  - Decompiled client source (`/tmp/client-assets/decompiled/ACorpBlazor/ACorpBlazor.6tqtyltacp.decompiled.cs`) at line 630 explicitly defines the key as a public constant:
    ```csharp
    public const string DefaultProfile = "Vu1nB1az0r$ecretKey!2026@@@@@@@@";
    ```
  - Line 632 confirms its usage: `private static byte[] ProfileBytes => Encoding.UTF8.GetBytes("Vu1nB1az0r$ecretKey!2026@@@@@@@@");`
  - Key length verified as 32 bytes via `wc -c` output.
- **Impact:** Any attacker with access to the client bundle can extract the key and decrypt/forge any data protected by this cipher, directly leading to credential theft.

### 2. Weak Cryptographic Implementation in TelemetryCodec
- **ID:** crypto_impl_telemetry_codec
- **Severity:** High
- **Proof Status:** DEMONSTRATED
- **Evidence:**
  - Code review of `TelemetryCodec` (lines 639–642, 679–682) confirms:
    - Algorithm: AES-256
    - Mode: CBC (`CipherMode=1`)
    - Padding: PKCS7 (`PaddingMode=2`)
    - IV: Randomly generated per encryption and prepended to ciphertext.
  - No MAC or integrity check (e.g., HMAC or GCM) is present in the implementation.
- **Impact:** Use of CBC mode without integrity protection allows ciphertext tampering (padding oracle/plaintext modification attacks). Combined with the hardcoded key, confidentiality and integrity are fully compromised.

### 3. Verbose Error Handling Leaking Stack Traces
- **ID:** finding_stack_trace_leak
- **Severity:** Medium
- **Proof Status:** DEMONSTRATED
- **Evidence:**
  - Sending a malformed ID to `/bookings/{Id}` returns HTTP 400 with full stack traces.
  - Example command: `curl -s "http://127.0.0.1:5000/bookings/null.json"`
  - Response excerpt:
    ```json
    {

        "errorCode": "SerializationException",
        "message": "Unable to bind to request 'QueryBookings'",
        "stackTrace": "System.Runtime.Serialization.SerializationException: ...\n   at ServiceStack.Serialization.StringMapTypeDeserializer.PopulateFromMap(...) in /home/runner/work/ServiceStack/ServiceStack/ServiceStack/src/ServiceStack.Client/Serialization/StringMapTypeDeserializer.cs:line 135\n   at ServiceStack.Host.RestPath.CreateRequest(...) in /home/runner/work/ServiceStack/ServiceStack/ServiceStack/src/ServiceStack/Host/RestPath.cs:line 462\n..."
      }

- **Impact:** Leaks internal directory structure, framework versions, and exact line numbers, significantly reducing the effort required for targeted exploitation or reverse engineering.

### 4. Plaintext Password Exposure via Decrypted User Token
- **ID:** creds_employee
- **Severity:** Critical
- **Proof Status:** DEMONSTRATED
- **Evidence:**
  - User info endpoint `/users/info/029d65c2-bd85-483f-8ef2-6f5f87e9bf84.json` returns `lastSeenToken`: `"jN/UHW7jw8/jGEykgwZhWSidf/DfnIJkvk2RRkoYnK4="`
  - Decryption using the extracted key (AES-256-CBC, IV prepended) yields the plaintext password:
    ```
    Decrypted: p@55wOrd
    ```
  - Authentication confirmed via POST to `/auth/login.json`:
    ```json
    {"userId":"029d65c2-bd85-483f-8ef2-6f5f87e9bf84","userName":"employee@email.com","displayName":"employee@email.com","roles":["Employee"]}
    ```
- **Impact:** Full account takeover of Employee accounts. The attack chain is fully automated: extract key → decrypt token → obtain password → authenticate.

## Recommendations

1. **Remove Hardcoded Keys Immediately**
   - Never embed cryptographic keys in client-side assemblies or source code.
   - Use a secure key management system (e.g., Azure Key Vault, AWS KMS) or server-side key derivation. If client encryption is required, use a key exchange protocol or wrap keys per-session.

2. **Implement Authenticated Encryption**
   - Replace AES-CBC with AES-GCM, or add an HMAC-SHA256 integrity check over the ciphertext.
   - Ensure all cryptographic operations include both confidentiality and integrity verification.

3. **Disable Detailed Error Reporting in Production**
   - Configure the API to return generic error messages (e.g., "Invalid request") instead of stack traces.
   - Log full exceptions server-side only; never expose `responseStatus.stackTrace` to clients.

4. **Stop Storing/Transmitting Plaintext Passwords**
   - Tokens should never decrypt to plaintext passwords.
   - Use secure, opaque authentication tokens (e.g., JWT with proper signing, short-lived session tokens).
   - Ensure passwords are hashed using a strong adaptive algorithm (e.g., Argon2, bcrypt) and never derived from reversible encryption.

5. **Rotate Compromised Keys and Credentials**
   - The key `Vu1nB1az0r$ecretKey!2026@@@@@@@@` must be considered fully compromised.
   - Force password resets for all accounts where `LastSeenToken` or similar structures were used.
