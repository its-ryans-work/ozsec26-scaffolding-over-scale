## Executive Summary

# Penetration Test Report: http://127.0.0.1:5000

## 1. Executive Summary
The assessment of the ACorpBlazor application identified critical weaknesses in its client-side security architecture and API access controls. A hardcoded AES-256 encryption key was found in the decompiled client assembly, enabling potential decryption or forgery of sensitive payloads. Additionally, multiple API endpoints expose business logic and user data without authentication, and an action-based batch dispatch mechanism may allow bypassing role-based access controls. These issues collectively risk unauthorized data access, privilege escalation, and exploitation of internal services.

## 2. Findings

### Finding 1: Hardcoded AES-256 Symmetric Key in Client Assembly
- **Severity:** High
- **Status:** DEMONSTRATED
- **Evidence Source:** Decompiled shared assembly (`ACorpBlazor.6tqtyltacp.decompiled.cs`)
- **Details:**
  A hardcoded encryption key is present in the `TelemetryCodec` class within the client-facing assembly. This key is used for AES-CBC encryption of telemetry and batch payloads, meaning an attacker can decrypt intercepted traffic or forge valid encrypted requests.
- **Concrete Evidence:**
  The following code was extracted via decompilation:
  ```csharp
  public static class TelemetryCodec
  {
      public const string DefaultProfile = "Vu1nB1az0r$ecretKey!2026@@@@@@@@";
      private static byte[] ProfileBytes => Encoding.UTF8.GetBytes("Vu1nB1az0r$ecretKey!2026@@@@@@@@");
      // ... uses ProfileBytes for AES-CBC encryption
  }
  ```
- **Impact:**
  Compromises confidentiality and integrity of encrypted communications. Allows attackers to construct valid payloads for endpoints requiring encryption (e.g., `/api/batch`).

### Finding 2: Exposed API Endpoints and Insufficient Access Controls
- **Severity:** High
- **Status:** DEMONSTRATED
- **Evidence Source:** API decompilation and anonymous HTTP testing
- **Details:**
  Multiple API endpoints are accessible without authentication or authorization checks, exposing user PII and business data. The application relies on client-side routing and role attributes (e.g., `[ValidateHasRole]`) that are not enforced server-side for these routes.
- **Concrete Evidence:**
  - Decompilation revealed endpoints such as `/bookings`, `/coupons`, and `/users/info/{UserId}`.
  - Anonymous requests returned sensitive data:
    ```http
    GET /users/info/029d65c2-bd85-483f-8ef2-6f5f87e9bf84.json
    Response: {"userId":"029d65c2-bd85-483f-8ef2-6f5f87e9bf84","userName":"employee@email.com","email":"employee@email.com",...}
    ```
    ```http
    GET /bookings.json
    Response: {"offset":0,"total":0,"results":[{"id":1,"name":"First Booking!","roomType":"Queen",...}]}
    ```
- **Impact:**
  Information disclosure of user identities, emails, and internal booking/coupon data. Facilitates further attacks such as credential stuffing or IDOR exploitation.

### Finding 3: Action-Based Batch Dispatch Endpoint
- **Severity:** High
- **Status:** INFERRED
- **Evidence Source:** Decompiled service model and application notes
- **Details:**
  The application exposes a generic dispatch endpoint (`POST /api/batch`) that accepts an `Action` string and a `Payload`. This pattern suggests server-side routing based on client-supplied input. While direct exploitation was not fully demonstrated in the captured output, the architecture allows potentially restricted actions (e.g., `SendEmail`, `QueryUsers`) to be invoked if the handler does not enforce server-side authorization.
- **Concrete Evidence:**
  - Service model definition:
    ```csharp
    [Route("/api/batch", "POST")]
    public class BatchRequest : IPost, IVerb, IReturn<BatchResponse>
    {
        public string Action { get; set; }
        public string Payload { get; set; }
    }
    ```
  - Notes indicate `SendEmail` is marked `InternalOnly` but may be callable via this mechanism.
- **Impact:**
  Potential privilege escalation and unauthorized execution of internal-only or administrative functions. If combined with the hardcoded encryption key, an attacker can forge encrypted batch requests to perform actions outside their role.

## 3. Recommendations

1. **Remove Hardcoded Credentials:**
   - Extract the AES key from the client assembly. Use a secure key management system or environment variables for server-side key storage. If client-side encryption is required, use a key exchange mechanism rather than a static shared secret.

2. **Enforce Server-Side Access Controls:**
   - Implement robust authentication and authorization checks on all API endpoints. Do not rely on client-side routing or attributes. Ensure endpoints like `/users/info/{Id}` require valid authentication and enforce proper ownership checks to prevent IDOR.

3. **Harden the Batch Dispatch Endpoint:**
   - Restrict the `Action` parameter to a whitelist of allowed operations.
   - Enforce role-based access control within the batch handler before executing any action.
   - Ensure internal-only actions (e.g., `SendEmail`) cannot be invoked from untrusted clients, regardless of input format.

4. **Implement Secure Communication Practices:**
   - Ensure all sensitive data is transmitted over TLS.
   - Validate and sanitize all inputs, especially in dynamic dispatch endpoints, to prevent injection or abuse.
