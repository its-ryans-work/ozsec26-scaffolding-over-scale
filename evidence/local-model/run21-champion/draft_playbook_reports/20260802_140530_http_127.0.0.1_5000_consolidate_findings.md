# Penetration Test Findings Report
**Target:** http://127.0.0.1:5000

## Executive Summary
The assessment identified critical weaknesses in the application’s cryptographic design and error handling that directly enable account compromise. A hardcoded AES-256 key shipped in the client assembly allows attackers to decrypt sensitive tokens, which was demonstrated by recovering a valid employee password and successfully authenticating. Additionally, verbose error responses leak internal stack traces, providing detailed implementation information that facilitates further exploitation. Immediate remediation of key management, encryption practices, and error handling is required.

## Findings

### 1. Hardcoded AES-256 Symmetric Key in Client Assembly
- **Severity:** Critical
- **Proof Status:** DEMONSTRATED
- **Evidence:** Decompilation of the client assembly (`ACorpBlazor.6tqtyltacp.dll` → `/tmp/client-assets/decompiled/ACorpBlazor/ACorpBlazor.6tqtyltacp.decompiled.cs`) revealed the `TelemetryCodec` class contains a static constant string used as the encryption key: `Vu1nB1az0r$ecretKey!2026@@@@@@@@` (32 bytes). This key is fully recoverable by any user with access to the client bundle and is used by `TelemetryCodec.Encode()` and `TelemetryCodec.Decode()`.
- **Source:** Client-side decompilation analysis; saved note `secret_aes_key`.
- **Impact:** Complete loss of confidentiality and integrity for all data encrypted with this key, including authentication tokens and telemetry.

### 2. Cryptographic Implementation Weaknesses (CBC Mode, No Integrity Protection)
- **Severity:** High
- **Proof Status:** DEMONSTRATED
- **Evidence:** Code review of the decompiled `TelemetryCodec` class shows the implementation uses AES-256-CBC with PKCS7 padding. The IV is randomly generated per encryption, prepended to the ciphertext, and the entire payload is Base64-encoded. No message authentication code (MAC/HMAC) or authenticated encryption mode is used. This matches CWE-798 (Hard-coded Cryptographic Key) and CWE-327 (Use of a Broken or Risky Cryptographic Algorithm).
- **Source:** Decompiled client assembly analysis; saved note `crypto_impl_telemetry_codec`.
- **Impact:** Lack of integrity protection enables ciphertext tampering and potential padding oracle attacks. Combined with the exposed key, an attacker can forge or alter encrypted tokens.

### 3. Verbose Error Handling Leaks Internal Stack Traces
- **Severity:** High
- **Proof Status:** DEMONSTRATED
- **Evidence:** Submitting malformed or unsupported inputs to API endpoints returns HTTP 400/404 responses containing a `responseStatus.stackTrace` field with full internal file paths and line numbers. For example, `/tmp/stack_trace_evidence.json` shows:
  ```json
  {"responseStatus":{"errorCode":"NotImplementedException","message":"The operation does not exist for this service","stackTrace":"System.NotImplementedException: The operation does not exist for this service\n   at ServiceStack.Host.Handlers.GenericHandler.CreateRequestAsync(IRequest req, String operationName) in /home/runner/work/ServiceStack/ServiceStack/ServiceStack/src/ServiceStack/Host/Handlers/GenericHandler.cs:line 30\n   at ServiceStack.Host.Handlers.GenericHandler.ProcessRequestAsync(IRequest httpReq, IResponse httpRes, String operationName) in /home/runner/work/ServiceStack/ServiceStack/ServiceStack/src/ServiceStack/Host/Handlers/GenericHandler.cs:line 79\n","errors":[]}}
  ```
  Similar behavior was observed on `/bookings/{Id}` with invalid types, exposing paths like `StringMapTypeDeserializer.cs:line 135` and `RestHandler.cs:line 145`.
- **Source:** HTTP response inspection; saved note `finding_stack_trace_leak`.
- **Impact:** Exposes internal architecture, framework versions, and source file locations, significantly aiding attackers in crafting targeted exploits.

### 4. Employee Account Compromise via Token Decryption and Key Reuse
- **Severity:** Critical
- **Proof Status:** DEMONSTRATED
- **Evidence:** Using the hardcoded AES key from Finding 1, the `LastSeenToken` value retrieved from `/users/info/{userId}` was decrypted to reveal the plaintext password `p@55wOrd`. Authentication was then successfully performed at `/auth/login.json` using `employee@email.com` / `p@55wOrd`, which returned a valid session with `roles=[Employee]`.
- **Source:** Cryptographic decryption and API authentication test; saved note `creds_employee`.
- **Impact:** Direct unauthorized access to user accounts. Any token encrypted with this key that contains credentials or session data can be trivially recovered and abused.

## Recommendations

1. **Remove Hardcoded Keys Immediately:**
   - Never embed cryptographic keys in client assemblies or source code.
   - Use a secure key management system (e.g., cloud KMS, hardware security module, or environment-based secrets) and inject keys at runtime via a secure backend.

2. **Implement Authenticated Encryption:**
   - Replace AES-CBC with an authenticated mode such as AES-GCM, or add a strong HMAC (e.g., HMAC-SHA256) over the ciphertext to ensure integrity and prevent tampering.

3. **Disable Verbose Error Responses in Production:**
   - Configure the application and ServiceStack framework to return generic error messages (e.g., "Bad Request" or "Internal Server Error") to external clients.
   - Log detailed stack traces server-side only, ensuring they are never exposed in HTTP responses.

4. **Rotate Compromised Credentials and Tokens:**
   - Force a password reset for the affected `employee@email.com` account and any other accounts whose tokens may have been encrypted with the compromised key.
   - Invalidate all existing tokens issued using the exposed key and reissue them using a new, securely managed key.

5. **Review Token Payloads:**
   - Ensure tokens do not contain plaintext passwords or sensitive credentials. Use opaque identifiers or securely encrypted claims with proper integrity protection.
