# PentestAgent Penetration Test Report

## Executive Summary

## Executive Summary

The assessment of http://127.0.0.1:5000 identified a hardcoded AES-256 symmetric key and an insecure cryptographic implementation within the client-side TelemetryCodec, alongside verbose error handling that exposes internal .NET stack traces. These issues allow adversaries to extract the encryption key, potentially decrypt or forge telemetry payloads, and map internal code structure to aid further exploitation. Immediate remediation is required to remove secrets from client code, adopt authenticated encryption, and suppress detailed error information in production responses.

## Findings

### 1. Hardcoded AES-256 Key & Insecure Cryptographic Implementation (TelemetryCodec)
- **Severity:** High
- **Proof Level:** DEMONSTRATED (via static analysis of decompiled client assembly)
- **Description:** The `TelemetryCodec` class in the client assembly contains a static, plaintext AES-256 key shipped directly to the client. The implementation uses AES-CBC with PKCS7 padding and a random IV prepended to the ciphertext, but lacks any message authentication code (MAC) or integrity check.
- **Evidence:** 
  - Saved notes `secret_aes_key` and `crypto_impl_telemetry_codec` document the key and implementation details observed during assembly decompilation.
  - Key value: `Vu1nB1az0r$ecretKey!2026@@@@@@@@` (32 bytes, static const string).
  - Implementation details: `CipherMode=1` (CBC), `PaddingMode=2` (PKCS7), IV randomly generated and prepended, output Base64-encoded. Explicitly noted: "No MAC/integrity protection."
- **Impact:** Any user with access to the client binary can extract the key and decrypt all telemetry data protected by this codec. Without integrity protection, ciphertext can be tampered with (bit-flipping/padding oracle-style manipulations) to alter decrypted values if the receiver does not validate payloads server-side.
- **CWE:** CWE-798 (Use of Hard-coded Cryptographic Key), CWE-327 (Use of a Broken or Risky Cryptographic Algorithm)

### 2. Verbose Error Handling Exposes Internal Stack Traces
- **Severity:** Medium
- **Proof Level:** DEMONSTRATED (per assessment notes of observed HTTP 400 responses)
- **Description:** Supplying malformed ID values to `/bookings/{Id}` triggers detailed .NET exception responses that include full stack traces, internal file paths, and line numbers. This occurs when the deserializer encounters unexpected types (e.g., null, float, overflow integers, arrays, or SQL-like strings).
- **Evidence:**
  - Saved note `finding_stack_trace_leak`: "Malformed ID inputs leak full .NET stack traces with internal file paths and line numbers. Example: SerializationException from StringMapTypeDeserializer.cs:line 135, RestPath.cs:line 462, RestHandler.cs:line 145. Occurs on /bookings/{Id} with invalid types... HTTP 400 with responseStatus.stackTrace exposed."
- **Impact:** Exposed internals facilitate reconnaissance, help attackers identify framework versions, locate vulnerable deserialization or routing logic, and craft more targeted exploits.
- **CWE:** CWE-209 (Generation of Error Message Containing Sensitive Information)

## Recommendations

1. **Remove hardcoded secrets from client code:**
   - Extract the AES key from `TelemetryCodec` and manage it server-side.
   - Use a secure key management service or environment-based configuration for server-side secrets.
   - Rotate the exposed key immediately and invalidate any data encrypted with it if confidentiality is required.

2. **Adopt authenticated encryption:**
   - Replace AES-CBC with an authenticated mode (e.g., AES-GCM) or add a strong MAC (e.g., HMAC-SHA256) over ciphertext.
   - Validate integrity server-side before processing decrypted payloads.

3. **Suppress detailed error information in production:**
   - Configure ASP.NET Core / ServiceStack to return generic error responses (e.g., HTTP 400 Bad Request or 500 Internal Server Error) without stack traces.
   - Disable detailed exceptions in production environments and log full traces server-side only.
   - Validate and sanitize route parameters (e.g., `{Id}`) before they reach deserialization/routing logic to prevent unexpected exception paths.
