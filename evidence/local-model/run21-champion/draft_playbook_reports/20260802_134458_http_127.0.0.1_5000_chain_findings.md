# PentestAgent Penetration Test Report

## Executive Summary

### Executive Summary
The assessment of http://127.0.0.1:5000 identified critical cryptographic and authentication flaws that allow full credential compromise and authenticated access. A hardcoded AES-256 key in the client assembly enables decryption of sensitive tokens, directly yielding user passwords and enabling login. Additionally, the encryption implementation lacks integrity protection, and unhandled errors expose detailed server stack traces, aiding further exploitation.

### Findings

#### 1. Hardcoded Cryptographic Key in Client Assembly
*   **Severity:** Critical
*   **Proof Status:** DEMONSTRATED
*   **Evidence:** Decompilation of `ACorpBlazor.dll` reveals a static constant used as an AES-256 key:
    *   Source: `ACorpBlazor.6tqtyltacp.decompiled.cs`, line 630: `public const string DefaultProfile = "Vu1nB1az0r$ecretKey!2026@@@@@@@@";`
    *   The key is exactly 32 bytes and is used by `TelemetryCodec.Encode()` and `Decode()` for AES-CBC encryption/decryption. Its presence in the client binary makes it fully recoverable by any user.
*   **Source:** Static analysis of `ACorpBlazor.6tqtyltacp.dll`

#### 2. Weak Cryptographic Implementation (No Integrity Protection)
*   **Severity:** High
*   **Proof Status:** INFERRED
*   **Evidence:** Code review of the `TelemetryCodec` class shows:
    *   Algorithm: AES-256-CBC (`CipherMode=1`) with PKCS7 padding (`PaddingMode=2`).
    *   IV: Randomly generated per operation and prepended to ciphertext.
    *   Missing: No HMAC or MAC is computed or verified during `Decode()`. This allows ciphertext tampering (bit-flipping attacks) without detection, as only confidentiality is enforced, not integrity.
*   **Source:** Code review of `TelemetryCodec.Encode()` and `TelemetryCodec.Decode()`

#### 3. Server-Side Stack Trace Information Disclosure
*   **Severity:** Medium
*   **Proof Status:** DEMONSTRATED
*   **Evidence:** Submitting malformed inputs to `/bookings/{Id}` (e.g., `/bookings/null.json`) triggers a `SerializationException` and returns an HTTP 400 response containing `responseStatus.stackTrace`. The trace exposes internal file paths and line numbers, such as:
    *   `StringMapTypeDeserializer.cs:line 135`
    *   `RestPath.cs:line 462`
    *   `RestHandler.cs:line 145`
*   **Source:** HTTP testing of `/bookings/{Id}` with invalid types

#### 4. Credential Exposure via Decrypted Session Token
*   **Severity:** Critical
*   **Proof Status:** DEMONSTRATED
*   **Evidence:**
    *   Retrieved `lastSeenToken` from `/users/info/029d65c2-bd85-483f-8ef2-6f5f87e9bf84.json`.
    *   Decrypted the token using the hardcoded `TelemetryCodec` key, yielding the plaintext password: `p@55wOrd`.
    *   Submitted credentials (`employee@email.com` / `p@55wOrd`) to `/auth/login.json`, which returned a successful authentication response with `userId`, `userName`, and `roles=[Employee]`.
*   **Source:** API interaction and cryptographic verification

### Recommendations
1. **Remove hardcoded keys:** Never embed cryptographic keys in client assemblies. Use server-side key management, HSMs, or secure configuration stores. If encryption is only for transport, rely on TLS.
2. **Implement authenticated encryption:** Replace AES-CBC with AES-GCM, or add a secure HMAC (e.g., HMAC-SHA256) over the ciphertext to ensure integrity and prevent tampering.
3. **Disable detailed error reporting:** Configure the application to return generic error messages in production. Ensure stack traces and internal paths are never exposed to clients.
4. **Secure token storage:** Do not encrypt or store credentials (even hashed or as tokens) in reversible client-side structures without strong, unique keys per user or session.
