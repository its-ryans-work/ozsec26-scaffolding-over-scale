# PentestAgent Penetration Test Report

## Executive Summary

# 1. Executive Summary
Static analysis of the decompiled client assembly for http://127.0.0.1:5000 identified a hardcoded AES-256 symmetric key shipped directly in the `TelemetryCodec` class. The cryptographic implementation uses AES-CBC without an integrity check (MAC), exposing telemetry payloads to decryption and manipulation by any attacker with access to the client binary. Immediate key rotation, removal of secrets from client-side code, and adoption of authenticated encryption are required to restore confidentiality and integrity.

# 2. Findings

## Finding 1: Hardcoded Cryptographic Key in Client Assembly (CWE-798)
**Severity:** High  
**Proof Level:** DEMONSTRATED (code artifact extraction)

A static AES-256 key is embedded as a `const string` in the client assembly and used directly for encryption/decryption. Because the key is shipped with the client, it is trivially recoverable via decompilation and does not provide confidentiality against offline analysis.

**Evidence:**
- Command: `sed -n '628,700p' /tmp/client-assets/decompiled/ACorpBlazor/ACorpBlazor.6tqtyltacp.decompiled.cs`
- Output (excerpt):

      private static byte[] ProfileBytes => Encoding.UTF8.GetBytes("Vu1nB1az0r$ecretKey!2026@@@@@@@@");

      {
          Aes val = Aes.Create();

**Source:** `ACorpBlazor.6tqtyltacp.decompiled.cs`, lines 628–640.

**Impact:** An attacker possessing the client binary can decrypt all telemetry data and forge valid encrypted payloads without needing network access or additional credentials.

## Finding 2: Insecure Cryptographic Implementation – CBC Without Integrity Protection (CWE-327)
**Severity:** Medium  
**Proof Level:** INFERRED (from code analysis)

The `TelemetryCodec` uses AES in CBC mode with PKCS7 padding and a randomly generated IV prepended to the ciphertext. However, no message authentication code (MAC) or authenticated encryption mode is used, leaving the scheme vulnerable to ciphertext tampering (e.g., bit-flipping or padding oracle attacks).

**Evidence:**
- Command: `sed -n '628,700p' /tmp/client-assets/decompiled/ACorpBlazor/ACorpBlazor.6tqtyltacp.decompiled.cs`
- Output (excerpt):
  ```csharp
  ((SymmetricAlgorithm)val).Mode = (CipherMode)1;   // CBC
  ((SymmetricAlgorithm)val).Padding = (PaddingMode)2; // PKCS7
  ((SymmetricAlgorithm)val).GenerateIV();
  ...
  byte[] array2 = new byte[((SymmetricAlgorithm)val).IV.Length + array.Length];
  Buffer.BlockCopy(((SymmetricAlgorithm)val).IV, 0, array2, 0, ((SymmetricAlgorithm)val).IV.Length);
  ```
  No HMAC, signature, or GCM usage is present in the `TelemetryCodec` class.
**Source:** `ACorpBlazor.6tqtyltacp.decompiled.cs`, lines 628–700.

**Impact:** While confidentiality relies on the key, the lack of integrity protection allows an attacker who can intercept or modify telemetry traffic to alter decrypted plaintext predictably or trigger errors on the server. Exploitation against the live endpoint was not executed during this assessment.

# 3. Recommendations

1. **Rotate the exposed key immediately:** Treat `"Vu1nB1az0r$ecretKey!2026@@@@@@@@"` as compromised. Generate a new AES-256 key and deploy it via a secure backend or runtime configuration mechanism.
2. **Remove all secrets from client assemblies:** Do not store cryptographic keys, tokens, or credentials as `const` or `static` strings in client-side code. Use secure key management (e.g., backend-held keys, envelope encryption, or secure enclaves) and fetch secrets at runtime where appropriate.
3. **Implement authenticated encryption:** Replace AES-CBC with an authenticated mode such as AES-GCM, or add a secure MAC (e.g., HMAC-SHA256) over the ciphertext and IV to prevent tampering.
4. **Assess telemetry sensitivity:** Review what data is transmitted via `TelemetryCodec`. If it contains PII, credentials, or business-critical information, treat this finding as critical and prioritize remediation accordingly.
5. **Add cryptographic tests:** Include unit/integration tests that verify encryption/decryption behavior, key storage practices, and integrity checks to prevent regression.

Phase: Find embedded and exposed key material
Objective: Anything shipped to a client is public. 
Techniques:
  1. Search decompiled or unpacked client artifacts - never the raw binaries or minified bundles, which hide literals. 
  2. Search along independent axes and iterate, designing patterns yourself: BY NAME (identifiers suggesting secrets), BY DECLARATION (compile-time constants and static fields), BY SHAPE (long unbroken high-entropy or base64/hex-like literals), BY USE (cryptographic and auth APIs and what is passed to them), BY CONFIG (endpoints, connection strings). 
  3. A name-based search is NOT evidence of absence: real secrets are often obfuscated so no dictionary word appears, and are declared under neutral names. The axes that ignore naming are the ones that find those. 
  4. Trace indirection: a crypto call usually references an identifier, not a literal. Follow it to the value, expecting several hops, and report the value rather than the variable name. 
  5. Secret scanners are worth running as an extra signal but detect mostly known provider credential formats; a clean scanner result must never be reported as 'no secrets present'. 

Phase: Assess how cryptography is used
Objective: Weak use of good primitives is as damaging as weak primitives. 
Techniques:
  1. Identify algorithms, modes, key sizes and IV or nonce handling, and whether integrity is protected as well as confidentiality. 
  2. Determine whether credentials are stored reversibly - encrypted or encoded rather than hashed. Reversible storage of a credential is a finding in itself. 
  3. For hashed material identify the algorithm and cost. Modern salted adaptive hashing should be reported as adequate; fast or unsalted hashing is a finding regardless of whether you crack it. 
  4. Assess whether tokens are random or derived from something predictable or recoverable. 

Phase: Join the key to the material
Objective: The step that converts two moderate findings into a critical one. 
Techniques:
  1. Before using a recovered secret: strip whitespace and quotes, print its length and bytes, and assert the length is valid for the algorithm. An invalid length means an extraction bug, not a wrong secret - go back and re-read the literal. 
  2. STOP AND JOIN THEM - the moment you hold BOTH a secret AND any opaque stored value (encrypted token, protected field, cookie, unexplained blob), attempt to decode that value with that secret as your NEXT action, before writing either up. Reported separately they read as 'a key leaked' and 'some data leaked'; joined they are frequently FULL ACCOUNT TAKEOVER. Assume the join works and disprove it. 
  3. Apply the secret to every opaque value you hold, for every account, not only the first. 
  4. Reimplement the owner's routine exactly from recovered source, and enumerate accepted operations from that source before composing requests. Never invent an operation name: it is rejected as unknown even when the material is correct. 
  5. Prove your implementation before trusting a rejection: round trip a known value, and decode something the TARGET produced. 
  6. If a plaintext credential results, hand it to authentication testing - recovering it is not the end of the chain. 

Phase: Verify before reporting
Objective: Apply the same evidence standard to every finding, so results are comparable across categories.
Techniques:
  1. PROOF DISCIPLINE - label every finding DEMONSTRATED (you executed it and the response proves it, quote that response), INFERRED (follows from evidence but was not executed), or UNVERIFIED (suspected from a version, component or code pattern only). Identifying software is never a demonstration; never write 'confirmed' without having executed something. 
  2. RUN THE CONTROL TEST. Before claiming any access or bypass, repeat the request WITHOUT the credential, token, header or material you believe is responsible. If the result is the same, you have proven nothing - the resource was already reachable. State the control result alongside the finding. This single omission is the most common source of false critical findings. 
  3. BUDGET DISCIPLINE - rank leads by evidence strength (material in hand > observed behaviour > suspicion from a version string) and give each a step budget. STOP RULE: about 8-10 consecutive steps on one lead with no new evidence means move on, recording what you tried. 
  4. Record findings to notes as you go, with the endpoint, the request, the response and the control result, so later phases and the report can use them. 
  5. Stay non-destructive: prefer read-only proof, do not modify or delete data, do not lock accounts, and stop once the point is demonstrated.
