### 1. Executive Summary

The assessment of `http://127.0.0.1:5000` (Vuln Blazor) identified significant access control issues on the ServiceStack API layer. While the Blazor WebAssembly frontend correctly enforces authentication via redirects for protected routes (e.g., `/secure/`), several backend API endpoints (`/api/QueryBookings`, `/api/QueryCoupons`) are accessible to unauthenticated users, potentially exposing sensitive data. Additionally, the `/api/CreateTodo` endpoint appears to lack authentication checks entirely, responding with parameter errors rather than authorization failures. ServiceStack metadata pages are also publicly accessible, aiding reconnaissance.

### 3. Recommendations

1.  **Enforce Authentication on API Endpoints:**
    *   Apply `[Authorize]` attributes or ServiceStack `RequiresAuthentication` filters to all query endpoints (`/api/Query*`) to prevent unauthenticated data access.
    *   Investigate the `/api/CreateTodo` endpoint immediately. It must enforce authentication before processing input parameters.

2.  **Disable ServiceStack Metadata in Production:**
    *   Disable the metadata feature or restrict access to `/metadata` and `/locode` to internal networks only.
    *   Example: `AppSettings.EnableFeatures(typeof(Features.Metadata))` should be disabled or secured.

3.  **Update Cookie Configuration:**
    *   Configure the Antiforgery cookie to include the `Secure` flag to ensure it is only transmitted over HTTPS.

4.  **Harden Server Headers:**
    *   Review server headers to reduce the disclosure of specific version numbers (e.g., ServiceStack 10.08, .NET 10) where possible, though framework headers are often difficult to remove entirely.

5.  **Review SPA vs. API Security Alignment:**
    *   Ensure that security logic is centralized in the backend API. The assessment showed that SPA routes (`/secure/`) redirect correctly, but the underlying APIs did not always enforce the same restrictions. Never rely solely on client-side (Blazor/Vue) route protection.
