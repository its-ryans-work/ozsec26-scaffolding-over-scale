# Penetration Test Report: http://127.0.0.1:5000

## Executive Summary
The assessment of http://127.0.0.1:5000 identified critical cryptographic and configuration weaknesses that directly enable credential compromise and information disclosure. A hardcoded AES-256 key embedded in the client-side assembly allows decryption of sensitive tokens, which was used to recover valid user passwords. Additionally, improper error handling exposes detailed .NET stack traces, and the cryptographic implementation lacks integrity verification, leaving data vulnerable to tampering. These issues collectively permit account takeover and significantly lower the barrier for further exploitation.

## Findings

### 1. Hardcoded Cryptographic Key in Client Assembly
- **Severity:** High
- **Status:** DEMONSTRATED
- **Evidence:** Decompiled client source (`/tmp/client-assets/decompiled/ACorpBlazor/ACorpBlazor.6tqtyltacp.decompiled.cs`, lines 630–632) contains:
  ```csharp
  public const string DefaultProfile = "Vu1nB1az0r$ecretKey!2026@@@@@@@@";
  private static byte[] ProfileBytes => Encoding.UTF8.GetBytes("Vu1nB1az0r$ecretKey!2026@@@@@@@@");
  ```
  This 32-byte string is used directly as the AES key within the `TelemetryCodec` class.
- **Source:** Client-side code analysis (decompiled Blazor WebAssembly assembly).
- **Impact:** Any attacker with access to the client bundle can extract the key, decrypt all data encrypted with it, and forge valid ciphertext.

### 2. Weak Cryptographic Implementation (TelemetryCodec)
- **Severity:** High
- **Status:** DEMONSTRATED
- **Evidence:** Code analysis of `TelemetryCodec.Encode()` (lines 634–650) shows:
  - Mode: CBC (`((SymmetricAlgorithm)val).Mode = (CipherMode)1;`)
  - Padding: PKCS7 (`((SymmetricAlgorithm)val).Padding = (PaddingMode)2;`)
  - IV: Generated randomly and prepended to ciphertext.
  - No MAC/HMAC or authenticated encryption is applied.
- **Source:** Client-side code analysis (same decompiled assembly).
- **Impact:** CBC without integrity protection is vulnerable to padding oracle attacks and ciphertext tampering. Combined with the hardcoded key, this allows attackers to modify encrypted payloads undetectably.

### 3. Information Disclosure via Stack Trace Leakage
- **Severity:** Medium
- **Status:** DEMONSTRATED
- **Evidence:** Sending malformed IDs to `/bookings/{Id}` returns HTTP 400 responses containing full stack traces. Example (`curl -s "http://127.0.0.1:5000/bookings/null.json"`):
  ```json
  {
    "responseStatus": {
      "errorCode": "SerializationException",
      "message": "Unable to bind to request 'QueryBookings'",
      "stackTrace": "System.Runtime.Serialization.SerializationException: ...\n   at ServiceStack.Serialization.StringMapTypeDeserializer.PopulateFromMap(...) in /home/runner/work/ServiceStack/ServiceStack/ServiceStack/src/ServiceStack.Client/Serialization/StringMapTypeDeserializer.cs:line 135\n   at ServiceStack.Host.RestPath.CreateRequest(...) in /home/runner/work/ServiceStack/ServiceStack/ServiceStack/src/ServiceStack/Host/RestPath.cs:line 462\n..."
    }
  }
  ```
  Confirmed with inputs: `null`, `1.5`, `'%20OR%201=1--`, `2147483648`, and `%5B1,2,3%5D`.
- **Source:** API fuzzing and error response analysis.
- **Impact:** Exposes internal file paths, library versions, and code structure, aiding attackers in crafting targeted exploits.

### 4. Credential Exposure via Decryption of LastSeenToken
- **Severity:** High
- **Status:** DEMONSTRATED
- **Evidence:**
  - Retrieved user info: `curl -s "http://127.0.0.1:5000/users/info/029d65c2-bd85-483f-8ef2-6f5f87e9bf84.json"` returned `"lastSeenToken":"jN/UHW7jw8/jGEykgwZhWSidf/DfnIJkvk2RRkoYnK4="`.
  - Decrypted using the hardcoded key and AES-CBC (IV prepended):
    ```python
    # Output of decryption script
    p@55wOrd
    ```
  - Assessment notes confirm this plaintext value was successfully used to authenticate at `/auth/login.json` for user `employee@email.com` with role `Employee`.
- **Source:** API data extraction and cryptographic decryption using the key from Finding 1.
- **Impact:** Direct account takeover. The `LastSeenToken` stores the user’s password in reversible encryption using a known key.

## Recommendations

1. **Remove Hardcoded Keys:** Never embed cryptographic keys in client-side code. Use a secure key management system or server-side key derivation. Rotate the exposed key immediately and invalidate all tokens/data encrypted with it.
2. **Strengthen Cryptographic Implementation:** Replace AES-CBC with an authenticated encryption mode (e.g., AES-GCM). Ensure all sensitive data is encrypted with unique, randomly generated keys per tenant/session, never static constants.
3. **Fix Error Handling:** Disable detailed stack trace exposure in production. Configure ServiceStack and the underlying framework to return generic error messages to clients while logging full details server-side only.
4. **Secure Credential Storage:** Never store passwords or authentication secrets in reversible encryption, especially with client-exposed keys. Use a strong, salted one-way hash (e.g., Argon2, bcrypt) for password storage. Treat `LastSeenToken` as sensitive session data and encrypt it server-side with keys never accessible to the client.
