# PentestAgent Penetration Test Report

## Executive Summary

# Executive Summary
The assessment of http://127.0.0.1:5000 identified a hardcoded AES-256 encryption key in the client-side assembly, multiple publicly accessible API endpoints exposing booking and user data, and a generic batch dispatch endpoint that may allow invocation of internal-only service methods. These findings indicate weak cryptographic key management, excessive API exposure, and potential for unauthorized internal method execution. Immediate remediation is required to rotate the exposed key, restrict API access, and validate batch endpoint authorization controls.

# Findings

## 1. Hardcoded AES-256 Key in TelemetryCodec Class
- **Severity:** High
- **Status:** INFERRED (key presence observed in decompiled assembly; cryptographic usage not executed/tested)
- **Description:** A 32-byte symmetric key used for AES-CBC-2 encryption of telemetry data is hardcoded in the `TelemetryCodec` class within the `ACorpBlazor` shared assembly. Exposure of this key allows decryption of any telemetry data encrypted with it.
- **Evidence:** Key value identified in decompiled source: `Vu1nB1az0r$ecretKey!2026@@@@@@@@`.
- **Source:** Saved notes (`secret_aes_key`); static analysis of `ACorpBlazor.6tqtyltacp.decompiled.cs`.

## 2. API Endpoints Discovered via Client Decompilation
- **Severity:** Info
- **Status:** DEMONSTRATED (endpoints exist and return data; no authentication required)
- **Description:** Multiple REST API endpoints were identified in the decompiled client assembly and verified live on the target. Several endpoints expose structured business data without visible authentication.
- **Evidence:** Live HTTP requests returned 200 OK and JSON data for:
  - `GET /bookings` – Returns booking records including employee names and email addresses.
  - `GET /coupons` – Returns discount coupon details.
  - `GET /todos` – Returns todo items.
  - `GET /users/id/{Id}` – Returns user UUIDs.
  - `GET /hello/{Name}` – Returns personalized greeting.
  - Swagger OpenAPI spec at `/swagger/v1/swagger.json` documents these routes.
- **Source:** Saved notes (`api_endpoints_from_decompile`); curl evidence; Swagger UI.

## 3. Generic Batch Dispatch Endpoint with Potential Internal Method Exposure
- **Severity:** Medium
- **Status:** UNVERIFIED (endpoint exists; dispatch behavior and internal method accessibility not tested)
- **Description:** The `POST /api/batch` endpoint accepts `Action` and `Payload` parameters and appears to route requests to internal service handlers. The client assembly references a `SendEmail` action marked `InternalOnly`, which may be callable through this generic dispatcher without proper authorization checks.
- **Evidence:** OpenAPI specification at `/swagger/v1/swagger.json` defines the endpoint with `action` and `payload` fields. Decompiled source indicates `SendEmail` is flagged `InternalOnly` but is not explicitly excluded from the batch dispatcher.
- **Source:** Saved notes (`batch_endpoint_dispatch`); OpenAPI spec; decompiled assembly routes.

# Recommendations
- **Rotate the AES key:** Replace the hardcoded key with a runtime-injected secret (e.g., environment variable, key vault). Re-encrypt any telemetry data previously protected by the exposed key.
- **Restrict API access:** Implement authentication and authorization on all data-exposing endpoints (`/bookings`, `/users/id/{Id}`, etc.). Remove or protect endpoints that are not required for public-facing functionality.
- **Harden the batch endpoint:** Validate the `Action` parameter against an explicit allowlist of permitted operations. Ensure internal-only methods (e.g., `SendEmail`) cannot be invoked via the public batch dispatcher. Add server-side authorization checks independent of client-side flags.
